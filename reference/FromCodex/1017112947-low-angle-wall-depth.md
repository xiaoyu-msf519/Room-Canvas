# 低视角墙体遮挡与 C 盘空间处理

## 排查结论

上一阶段为消除渐变结束时的队列切换，在 Edit 中让所有墙保持透明混合并关闭深度写入。这样虽然材质 opacity 连续，墙体之间仍依赖 Three.js 按对象中心排序。长墙、门洞拆分面板与凹角在平视时容易出现绘制顺序与逐像素前后关系不一致；排序改变也不经过 opacity 动画。

对当前真实扫描数据，在六个固定水平位置从 7m 降到 0.3m 的抽样中，墙体目标透明度没有变化。这支持渲染排序问题的判断，不能据此推断所有位置的遮挡判定都完全正确。

## 实现

- Edit 使用 Three.js 内置 `alphaHash`，固定 `transparent=false`、`depthWrite=true`。半透明通过逐像素覆盖实现，保持深度遮挡，不再依赖透明对象的中心排序。
- 原有相机侧向与有限室内射线判定保留，L 型房间跨多个拐角的遮挡仍有效。
- 保留 opacity 在 1 与 0.18 间的 0.5s Cubic.Out 渐变；反向时从当前值继续，终点不切换材质队列与深度配置。
- Play 关闭 Alpha Hash、取消未完成渐变，立即恢复所有实墙。
- Alpha Hash 的代价是半透明区域存在细颗粒覆盖效果，本阶段没有增加时间抗锯齿与额外渲染通道。

## 验证

- `npm run verify:walls` 通过，覆盖普通房间与 L 型房间的低视角远墙保持不透明、近墙半透明。
- 当前 30 面板扫描在四个方位、7m/1.65m/0.25m 三种高度共 12 组组件检查通过；转动与降低相机时检查深度写入、Alpha Hash、材质版本和逐帧透明度连续性。
- 30/60/120fps 连续往返渐变、途中反向、减少动态效果、Play 立即恢复、轮询复用材质等回归通过。
- `npm run build` 通过，仅保留原有主包体积提示。
- 前端 `http://127.0.0.1:5173/`、后端场景接口均 HTTP 200，服务继续运行。
- 浏览器连接无可用实例，未完成真实 GPU 画面的目视验收；尤其仍需在页面确认细颗粒透明的视觉效果。

## 磁盘处理

C 盘最初仅剩 132,370,432 字节，接近满盘。清理范围仅限已核实的可重建缓存：

- 使用 npm 官方 `cache clean` 清理 C 盘 npm 包下载缓存。
- 将 VS Code 缓存的扩展安装包移至 `tmp/disk-cleanup/vscode-installers-20261017112819/`，可恢复，未卸载已安装扩展。
- Codex 当前运行时、项目资料、模型缓存、凭据与个人文档未清理。

直接递归删除多个缓存目录的操作被自动安全检查拦截；随后改用上述官方清理与可恢复迁移完成空间释放，没有继续删除崩溃转储。

完成后 C 盘剩余 4,195,729,408 字节，约 3.91GiB，释放约 3.78GiB。迁移的安装包位于被忽略的 `tmp/`，不会提交到 Git。
